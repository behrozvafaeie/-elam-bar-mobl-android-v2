# اعلام بار مبل — Android APK

برنامه بومی اندروید با Kotlin و Jetpack Compose؛ خروجی موردنظر فقط APK است و نسخه وب/PWA در محدوده پروژه نیست.

## وضعیت نسخه فعلی

- نسخه سورس: `1.0.22`، کد نسخه `23`
- Application ID: `ir.elambar.mobl`
- حداقل Android: API 24
- شاخه آزمایش و تکمیل: `work/release-hardening-1.0.22`
- شاخه مبنای کار: `work/source-186`
- APK شماره ساخت ۲۱۲ با موفقیت ساخته و Artifact آن منتشر شده است.
- کاربر نصب نسخه آزمایشی را روی گوشی خود تأیید کرده و صفحه اول و دو گزینه ورود را دیده است.
- این تأییدها به معنی تأیید کامل ورود، ثبت بار، چت، تماس یا آمادگی انتشار عمومی نیست.
- APK فعلی Debug-signed و صرفاً نسخه آزمایشی است؛ انتشار نهایی به کلید امضای Release و آزمون‌های پذیرش نیاز دارد.

## اصول حفاظت از پروژه

- شاخه‌های `stable/base-run-165`، `stable/base-run-162`، `fix/v152-login-vehicle-validation` و شاخه‌های کاری قبلی حفظ شوند.
- هیچ جدول، رکورد، فایل یا policy در Supabase بدون بررسی و اجازه صریح حذف نشود.
- تغییرات دیتابیس فقط به‌صورت migration افزایشی و با بررسی سازگاری انجام شوند.
- هیچ کلید `service_role`، رمز سروری یا کلید خصوصی داخل APK یا فایل‌های عمومی مخزن قرار نگیرد.
- موفقیت Build به‌تنهایی معادل آزمون نصب و عملکرد نیست.

## محدوده محصول

### نقش‌ها و حساب‌ها
- راننده، شرکت باربری، مدیران دارای مجوز و مدیر ارشد اصلی.
- مشتری امکان ورود ندارد.
- فرم‌های ثبت‌نام شامل نام، نام خانوادگی و اطلاعات اختصاصی هر نقش هستند.
- ورود راننده و شرکت در نسخه فعلی با نام کاربری و رمز عبور پیاده‌سازی شده است؛ ورود با شماره موبایل/پیامک هنوز باید جداگانه تکمیل و آزمایش شود.
- شرکت و راننده باید پیش از استفاده از قابلیت‌های محدودشده، وضعیت تأیید مناسب داشته باشند.

### اعلام بار و رانندگان
- مبدأ همه بارها تهران و ثابت است.
- شرکت می‌تواند مقصد یا چند مقصد را انتخاب و بارها را گروهی ثبت کند.
- انواع بار: دربست، روباری و نیم‌بار.
- انواع خودرو: وانت مبلی، کامیونت مبلی، کامیون ۶ متری، کامیون دربستی کار و خاور مبلی پتو‌دار.
- راننده می‌تواند چند مقصد انتخاب کند؛ تطبیق باید براساس نوع خودرو و مقصد انجام شود.
- راننده می‌تواند بار منتشرشده را بدون توافق قبلی بگیرد.
- شرکت فقط مجاز به مدیریت بارهای خودش در وضعیت‌های مجاز است.
- شرکت‌های تأییدشده باید بتوانند رانندگان مناسب را براساس خودرو و مقصد جست‌وجو کنند.

### پنل و تجربه کاربری
- مدیر ارشد اختیار کامل دارد؛ مدیران میانی فقط طبق مجوزهای صریح فعالیت می‌کنند.
- منوی کشویی و تنظیمات یکپارچه باید در همه نقش‌ها کامل و قابل استفاده باشند.
- تاریخ‌ها شمسی و زمان رویدادها مبتنی بر زمان سرور و منطقه زمانی تهران نمایش داده شوند.
- گزینه «برگشت» در صفحات جایگزین خروج ناخواسته شود؛ خروج از حساب جدا باشد.
- عکس پروفایل از گالری برای راننده، شرکت و مدیر پشتیبانی شود.

### پیام‌رسانی و تماس
- کد فعلی شامل صفحه/زیرساخت بخشی از پیام‌رسانی خصوصی، ارسال متن و ویس است.
- اتاق عمومی شرکت‌ها و مدیران، کنترل دقیق مجوز خواندن/ارسال رانندگان و کنترل تصویر/ویس توسط مدیر ارشد باید در آزمون و در صورت نیاز تکمیل شوند.
- تماس WebRTC بدون آزمون واقعی دو دستگاه، تماس آماده محسوب نمی‌شود.
- تنظیم STUN/TURN و مدیریت امن اعتبارنامه‌های موقت برای تماس پایدار لازم است.
- پیام‌ها و فایل‌های خصوصی باید با RLS و Storage خصوصی محافظت شوند.

## مراحل باقی‌مانده تا انتشار نهایی

1. **آزمون ورود و حساب‌ها:** ورود و ثبت‌نام راننده و شرکت، حساب تأییدنشده، حساب تأییدشده، حساب مسدود، بازیابی نشست و خروج.
2. **آزمون عملیات بار:** ثبت بار تکی و گروهی، چند مقصد، تطبیق خودرو/مقصد، گرفتن بار، رد بار، ویرایش و حذف فقط در وضعیت مجاز.
3. **آزمون پنل مدیر ارشد:** فهرست‌ها، بروزرسانی، تأیید/رد/مسدودسازی، مجوز مدیران و ثبت رویدادهای مدیریتی.
4. **آزمون ارتباطات:** پیام متنی، تصویر، ویس، دریافت و پخش، چت عمومی/خصوصی و کنترل مجوز هر نقش.
5. **آزمون تماس:** تماس واقعی بین دو دستگاه، مجوز میکروفن/دوربین، قطع و وصل شبکه و TURN.
6. **آزمون امنیت:** RLS، Storage، RPCها، Edge Functionها، توکن‌ها، کلیدها و تنظیمات Auth.
7. **آزمون دستگاه:** نصب، اجرای سرد، برگشت از پس‌زمینه، قطع اینترنت، نمایش فارسی/شمسی، اندازه صفحه و نبود crash.
8. **انتشار:** پیکربندی کلید امضای Release از طریق GitHub Actions Secrets، ساخت APK امضاشده Release، تأیید امضا و نصب به‌روزرسانی روی گوشی آزمایشی.

## گردش‌کار ساخت و آزمون

- Workflow: `.github/workflows/android-apk.yml`
- Artifact آزمایشی: `elam-bar-mobl-debug-apk`
- workflow ابتدا APK را می‌سازد، شناسه بسته/نسخه و امضا را بررسی می‌کند و Artifact را منتشر می‌کند.
- آزمون شبیه‌ساز یک مرحله جداگانه و فعلاً غیرمسدودکننده است؛ شکست آن نباید به‌اشتباه شکست ساخت APK تلقی شود.
- در آزمون شبیه‌ساز، APK نصب و اجرا و وجود process و خطای fatal بررسی می‌شود.

## اطلاعات Supabase

- پروژه از Supabase Auth، Postgres، RLS، RPC، Edge Functions و Storage استفاده می‌کند.
- تغییرات امنیتی و schema باید با migrationهای افزایشی انجام شوند.
- قبل از هر تغییر باید نام ستون‌ها، توابع، policyها و bucketهای موجود با سورس و پروژه واقعی تطبیق داده شود.
- کلیدهای حساس فقط در تنظیمات امن سرور یا GitHub Secrets نگهداری شوند.

## تعریف «آماده انتشار»

برنامه فقط زمانی آماده انتشار عمومی است که همه مراحل پذیرش بالا با نتیجه موفق ثبت شده باشند، APK با کلید Release پایدار امضا شده باشد و نصب/به‌روزرسانی آن روی گوشی واقعی تأیید شود. هر قابلیت آزمایش‌نشده باید صریحاً به‌عنوان آزمایش‌نشده باقی بماند.
