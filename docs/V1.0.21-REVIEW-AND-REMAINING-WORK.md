## یافته‌های بحرانی و نیازمند اصلاح سمت سرور

### ۱. ثبت بار با انواع خودرو

UI پنج نوع خودرو مصوب را ارسال می‌کند، اما تابع `private.publish_tehran_load_batch_v2` فقط این سه مقدار قدیمی را می‌پذیرد: `کامیون مبلی`، `کامیون ۶ متری` و `وانت`. بنابراین مقدارهای جدید UI مانند `وانت مبلی`، `کامیونت مبلی`، `کامیون ۶متری`، `کامیون دربستی کار` و `خاور مبلی پتو‌دار` با تابع فعلی هماهنگ نیستند و ثبت گروهی ممکن است رد شود. باید یک فهرست canonical واحد برای UI، Edge Functionها، RPC، قیود جدول و جست‌وجو تعریف و با تست یکپارچه تأیید شود.

### ۲. ثبت‌نام راننده و فهرست خودروها

تابع فعال مورد استفاده برنامه برای ثبت‌نام و ورود، `username-auth-v2` است. فهرست خودرو در این تابع با پنج گزینه مصوب برنامه یکسان نیست و شامل چند گزینه قدیمی است. تابع `device-register` نیز در پروژه فعال است ولی UI فعلی از `username-auth-v2` استفاده می‌کند؛ هر دو endpoint باید بررسی و از نظر اعتبارسنجی هماهنگ شوند. هیچ‌کدام در این بازبینی deploy نشده‌اند.

### ۳. چند نوع خودرو برای یک راننده

جدول `public.drivers` فقط ستون متنی `vehicle_type` دارد. RPC پذیرش بار و جست‌وجوی راننده نیز بر همان یک مقدار تکیه دارند. برای پشتیبانی از چند نوع خودرو، تغییر سازگار و بدون حذف داده لازم است: افزودن آرایه نوع خودرو، پر کردن آن از مقدار فعلی برای همه رانندگان، سپس تغییر ثبت‌نام، جست‌وجو، RLS و RPC پذیرش بار. تا زمان تکمیل این تغییر، نسخه ۱.۰.۲۱ هنوز فقط یک نوع خودرو را پشتیبانی می‌کند.

### ۴. مدارک راننده

قید دیتابیس `driver_documents_document_type_check` فقط `smart_card` و `driving_license` را قبول می‌کند؛ UI قبلی چهار عنوان فارسی می‌فرستاد و این باعث رد شدن درج مدرک می‌شد. نسخه ۱.۰.۲۱ نگاشت دو نوع پشتیبانی‌شده را اصلاح می‌کند. برای کارت ملی و کارت خودرو باید ابتدا قید و مدل داده به صورت migration بررسی و توسعه یابد. جایگزینی مدرک قبلی به جای صرفاً افزودن مدرک جدید نیز هنوز کامل نیست.

### ۵. پذیرش بار

تابع امن `public.driver_accept_load(p_load_id)` در Supabase وجود دارد و راننده تأییدشده را کنترل می‌کند، سپس بار منتشرشده و منطبق با نوع خودرو و مقصد را به صورت اتمیک به راننده اختصاص می‌دهد. برنامه قبلی فقط فهرست متنی بارها را نمایش می‌داد و این RPC را فراخوانی نمی‌کرد. نسخه ۱.۰.۲۱ اتصال اولیه UI به این RPC را اضافه می‌کند؛ آزمون با حساب واقعی راننده و رقابت دو راننده هنوز لازم است.

- پیام صوتی، ارسال تصویر/فایل در چت و تماس صوتی/تصویری هنوز عملیاتی نیستند؛ وجود جدول‌های messages و call_sessions به معنی وجود قابلیت در اپ نیست.
- تنظیمات فعلی محدود به پوسته، صدای اعلان، اندازه متن، زبان و نمایش تقویم است؛ تنظیمات حساب، امنیت، تغییر رمز و اعلان‌های واقعی تکمیل نشده‌اند.
- پروفایل بیشتر نمایشی است؛ ویرایش اطلاعات پایه حساب تکمیل نشده است.
- مدیریت مدارک فقط نمایش، تأیید و رد را دارد؛ دلیل رد، تاریخچه نسخه‌ها و جایگزینی امن مدرک نیازمند توسعه است.
- مسدودسازی حساب در UI دلیل ثابت می‌فرستد؛ دلیل اختصاصی، تعلیق زمان‌دار و ثبت تاریخ پایان تعلیق کامل نیست.
- تاریخ شمسی در ساعت بالای برنامه وجود دارد، اما همه تاریخ‌های دریافتی از پنل‌ها هنوز به صورت یکپارچه به شمسی تبدیل نشده‌اند.
- جست‌وجوی شرکت فقط یک نوع خودرو و یک مقصد را در هر درخواست می‌پذیرد.
- ورود مدیر با ایمیل انجام می‌شود و access token مدیر فقط در حافظه برنامه نگهداری می‌شود؛ refresh امن و بازیابی نشست مدیر تکمیل نشده است.
- کد اصلی در یک فایل بسیار بزرگ `MainActivity.kt` قرار دارد؛ تقسیم آن به ماژول‌های UI، data، auth، repository و admin برای نگهداری و تست‌پذیری لازم است.

## یافته‌های امنیتی Supabase

- هشدار Advisor برای `public.admin_set_member_status` به دلیل SECURITY DEFINER و قابل اجرا بودن برای نقش authenticated است. بررسی بدنه نشان داد تابع `auth.uid()`، نشست معتبر، `private.is_admin()`، مجوز ویرایش بخش و ثبت audit log را کنترل می‌کند؛ بنابراین نباید بدون بررسی مجوزها و تست، دسترسی آن را کورکورانه حذف کرد. با این حال بهتر است API سطح عمومی آن محدودتر یا در schema خصوصی قرار گیرد.
- Advisor هشدارهای anonymous access را برای چندین جدول گزارش می‌کند؛ علت مهم قابل بررسی، امکان anonymous sign-in همراه با policyهای نقش authenticated است. وضعیت Auth anonymous sign-ins باید در داشبورد تأیید و در صورت عدم نیاز خاموش شود؛ سپس سیاست‌ها دوباره ارزیابی شوند.
- ده جدول در schema خصوصی با RLS فعال و بدون policy گزارش شده‌اند. چون در schema خصوصی هستند، این وضعیت ممکن است عمدی باشد؛ برای رفع هشدار نباید بی‌دلیل policy عمومی ایجاد شود.
- وضعیت leaked-password protection باید در تنظیمات Auth دوباره تأیید شود؛ گزارش قبلی آن را خاموش نشان داده بود.
- health advisor در بررسی فعلی finding نداشت. performance advisor چند index استفاده‌نشده را INFO گزارش کرده؛ حذف index بدون مشاهده بار واقعی و بررسی query plan انجام نشود.
- هیچ تغییر schema، policy، function یا داده‌ای در Supabase در این بازبینی اعمال نشده است.
