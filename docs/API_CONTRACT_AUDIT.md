# ممیزی قرارداد API — یافته‌های مهم پیش از پیاده‌سازی

تاریخ بررسی: 2026-11-20
روش: خواندن تعریف توابع و کد Edge Functionها؛ هیچ تغییری در Supabase اعمال نشده است.

## تصمیم فعلی احراز هویت
- تصمیم محصول در تاریخ 2026-11-20: **فعلاً بدون پیامک و بدون OTP پیامکی**.
- مسیر مبنای نسخه جدید، ورود با شماره موبایل/نام کاربری و رمز عبور از طریق قرارداد فعلی `username-auth-v2` است؛ جزئیات دقیق ورودی/خروجی و صدور نشست باید هنگام پیاده‌سازی دوباره از کد تابع و کلاینت بررسی شود.
- مسیر OTP و اتصال Kavenegar به مرحله بعد موکول شده است؛ در این مرحله نباید پیامک OTP، هزینه پیامک یا وابستگی به Kavenegar در جریان ورود نمایش داده شود.
- Edge Function با نام `username-auth-v2` فعال است و عملیات register/login/reset دارد و بر اساس نام کاربری یا شماره موبایل به‌همراه رمز عبور کار می‌کند.
- Edge Function با نام `device-register` نیز حساب‌های شرکت/راننده می‌سازد و برای حساب‌های جدید رمز تصادفی سمت سرور می‌سازد؛ این مسیر به‌تنهایی ورود OTP یا نشست کاربر را فراهم نمی‌کند.
- پیش از اتصال کلاینت جدید، باید قرارداد دقیق نشست، ذخیره امن توکن، بازیابی رمز و رفتار حساب‌های قدیمی بررسی شود. هیچ حسابی حذف یا بازنشانی نشود.
- هیچ کد یا تنظیم احراز هویت در پروژه زنده تغییر نکرده است.

## ثبت بار
- تابع `private.publish_tehran_load_advanced_v1(p_items jsonb, p_publisher_type text, p_company_id uuid)` وجود دارد.
- این تابع چند مقصد را در یک فراخوانی می‌پذیرد و برای هر مقصد یک بار و چند `load_cargo_items` ایجاد می‌کند.
- مبدأ را در سمت سرور «تهران» قرار می‌دهد و نوع خودرو/بارگیری و کرایه را اعتبارسنجی می‌کند.
- در تعریف فعلی بررسی‌شده، نام اقلام مجاز فقط «مبل»، «سرویس خواب»، «اثاث منزل» و «تی‌وی کنسول» است؛ «ناهارخوری»، «مبل استیل» و «مبل کلاسیک» در فهرست مجاز این تابع نیستند.
- تابع برای تعداد عناصر آرایه سقف صریح پنج‌تایی ندارد، اما سقف عملیاتی/حفاظت در برابر payload بزرگ و محدودیت تجاری باید جداگانه تعیین شود.
- هر مقصد در هر item شامل مقصد، نوع خودرو، نوع بارگیری، کرایه، توضیحات و آرایه cargo_items است.
- `price_mode` می‌تواند `fixed` یا `negotiable` باشد؛ مقدار `negotiable` کرایه صفر می‌گذارد. این قابلیت باید در رابط کاربری فقط پس از تصمیم محصول نمایش داده شود.
- تابع قدیمی‌تر `publish_tehran_load_batch_v2` فقط `cargo_type` متنی ساده می‌گیرد و برای مدل چندقلمی مناسب نیست؛ از آن برای فرم جدید استفاده نشود مگر نیاز آن جداگانه ثابت شود.

## پذیرش بار
- `private.driver_accept_load(p_load_id uuid)` اتمیک است؛ فقط راننده تأییدشده و بار منتشرشده را می‌پذیرد.
- نوع خودرو و مقصد انتخاب‌شده راننده در شرط پذیرش کنترل می‌شود.
- این تابع وضعیت را به `driver_selected` تغییر می‌دهد و راننده را به بار اختصاص می‌دهد.
- مسیر «درخواست راننده و انتخاب شرکت» در این قرارداد تابع مستقلی که بررسی شد ندارد؛ پذیرش مستقیم موجود است. این تفاوت با مدل محصول باید پیش از پیاده‌سازی نهایی تعیین تکلیف شود.

## تطبیق راننده
- `private.search_approved_drivers_v2(p_vehicle_type,p_destination)` برای جست‌وجوی راننده تأییدشده توسط شرکت تأییدشده موجود است.
- مقصد اصلی یا آرایه destinations راننده بررسی می‌شود.

## چت
- `private.can_read_chat_room` و `private.can_send_chat_room_message` وجود دارند.
- مجوز پیام عمومی بر اساس نوع کاربر، عضویت، تنظیمات شرکت، mute/read-only و مجازبودن نوع رسانه کنترل می‌شود.
- کلاینت باید از این قواعد سروری تبعیت کند و نباید صرفاً دکمه‌ها را مخفی کند.

## تصمیم پیاده‌سازی
- تا رفع شکاف‌های فوق، هیچ‌یک از این موارد را در رابط کاربری به‌عنوان قابلیت عملیاتی قطعی نمایش نمی‌دهیم.
- تغییر توابع یا جداول موجود فقط پس از تهیه migration افزایشی، بازبینی SQL و تأیید کاربر انجام می‌شود.
- کلیدها و اسرار سرویس‌ها هرگز در APK یا مخزن GitHub قرار نمی‌گیرند.
